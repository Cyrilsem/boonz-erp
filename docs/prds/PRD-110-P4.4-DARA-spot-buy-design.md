## 1. THE THREE LANDMINES — each is live code, each breaks the naive build

### ⛔ L1. `receive_purchase_order` HARDCODES WH_CENTRAL. A spot buy for an MCC machine will not bind.

`receive_purchase_order` opens with `v_warehouse_id uuid := public.wh_central_id();` and every
`warehouse_inventory` INSERT it makes — lines **and** additions — uses that variable. There is no
warehouse argument. Meanwhile `bind_dispatch_fefo` picks stock with
`p.warehouse_id = COALESCE(rd.from_warehouse_id, public.wh_central_id())`.

**Consequence:** a driver spot-buys for a machine served by WH_MCC, the goods are received to
CENTRAL, and the binder looks in MCC. The line stays unbound, `blocked_demand` gets marked
`resolved='spot_buy'`, and **the board still shows nothing to pack.** That is a silent qty-0 by
another name — LAW 5.

⭐ **DESIGN DECISION D-A: `create_spot_purchase_v3` does NOT call `receive_purchase_order`.** It
takes `p_warehouse_id uuid NOT NULL` and performs its own receive into that warehouse, reusing the
batch-id convention and the NULL-expiry refusal verbatim. Rationale: the alternative — widening
`receive_purchase_order` with a warehouse argument — edits a **protected-entity writer used by the
whole procurement FE** to serve one new caller. Article 3 (versioned additions only) says add
`_v3`, do not mutate the incumbent. ⛔ **Do not "fix" `receive_purchase_order` as part of P4.4.**
That is a separate, FE-coupled unit; if CS wants it, it is its own PRD line with its own fixture.

⚠️ **Residual, and it must be recorded not hidden:** the spot goods now sit in the _correct_ WH, but
`purchase_orders.received_qty` is stamped by our RPC rather than by the incumbent receiver, so the
two receive paths must produce **byte-identical PO-side effects**. Fixture 18 asserts that column by
column (§5, seq 20-26).

### ⛔ L2. `create_purchase_order` FORCES A DRIVER TASK FOR EVERY WALK-IN SUPPLIER — backwards for a spot buy.

```
v_needs_task := (v_procurement_type = 'walk_in') OR (p_force_driver_task = true);
IF v_needs_task THEN INSERT INTO public.driver_tasks (... status 'pending' ...)
```

`p_force_driver_task => false` **cannot suppress this** — the OR makes walk-in unconditional. Every
spot-buy supplier is walk-in by definition.

**Consequence:** the RPC would mint a `pending` driver task instructing someone to go and buy goods
**that the driver has already bought and is holding in his hand.** Ops noise, and worse, a task
queue that trains people to ignore it.

⭐ **DESIGN DECISION D-B: call `create_purchase_order` (do NOT re-implement PO creation — it owns
`po_number_seq` drift self-healing, the PRD-1 `boonz_product_block_reason` guardrail, and
`procurement_events`), then immediately close the task it creates**, in the same transaction, with
an explicit reason. Concretely: after the call, `UPDATE public.driver_tasks SET status='completed',
notes = notes || ' [auto-closed: goods already purchased via create_spot_purchase_v3]' WHERE po_id =
v_po_id AND status='pending'`, and emit a `procurement_events` row `spot_purchase_task_autoclosed`.
⛔ **Never DELETE the task row** — memory rule "no destructive changes" and Article 7.
⭐ Reusing the incumbent creator is what keeps the PRD-1 blocked-product guardrail on the spot path.
A spot buy of a decommissioned product must fail exactly as a planned order does.

### ⛔ L3. THE BINDER ONLY TOUCHES ROWS THAT ARE UNPACKED, UNRETURNED, UNCANCELLED AND NOT M2M.

`bind_dispatch_fefo` targets `refill_dispatching` where `action IN ('Refill','Add','Add New')` AND
`from_wh_inventory_id IS NULL` AND `item_added=false` AND `returned=false` AND `cancelled=false` AND
`packed=false` AND `is_m2m=false`. It is also **plan-date + machine-name scoped**
(`p_machine_names text[]`, matched on `machines.official_name`).

⭐ **DESIGN DECISION D-C: `create_spot_purchase_v3` re-uses `bind_dispatch_fefo` unchanged**, called
with the single machine's `official_name` and the dispatch date — never with `NULL` (which would
sweep the whole fleet and bind unrelated machines' lines to our new batch as a side effect of one
driver's Carrefour run). ⛔ **A fleet-wide bind inside a single-machine RPC is the P4.4 equivalent of
re-running an engine over human edits.**
⚠️ Its return value `still_unbound_no_wh_stock` is the honest outcome signal and must be surfaced in
the RPC's return jsonb, **not swallowed**. A spot buy that bought the wrong thing binds nothing, and
the caller has to be told.

## 2. SIGNATURE (Dara)

```sql
public.create_spot_purchase_v3(
  p_machine_id      uuid,          -- the machine whose blocked demand this unblocks (NULL = pure WH top-up)
  p_warehouse_id    uuid,          -- ⛔ REQUIRED. L1. Where the goods physically land.
  p_supplier_id     uuid,          -- must be procurement_type='walk_in' AND status='Active'
  p_lines           jsonb,         -- [{boonz_product_id, qty, price_per_unit_aed, expiry_date}]
  p_dispatch_date   date   DEFAULT NULL,   -- defaults to resolve_refill_plan_date()
  p_receipt_photo   text   DEFAULT NULL,   -- storage path; nullable in wave 1
  p_po_id           text   DEFAULT NULL,   -- NULL ⇒ attach to today's open walk-in PO for this supplier, else mint
  p_note            text   DEFAULT NULL,
  p_dry_run         boolean DEFAULT false  -- ⭐ mandatory: this RPC touches 4 protected entities
) RETURNS jsonb
```

**SECURITY DEFINER**, `search_path=public, pg_temp`, `REVOKE ALL FROM PUBLIC` then
`GRANT EXECUTE TO service_role, authenticated` — ⛔ and per **S-140**, read `proacl` **back** and
assert the whole string; `REVOKE … FROM PUBLIC` removes nothing because the default grant is
per-role and explicit. Role gate inside: `field_staff` and up (a driver standing at Carrefour is the
primary caller), matching `create_purchase_order`'s own gate.

⭐ **`expiry_date` is REQUIRED per line, not optional.** `receive_purchase_order` raises
BUG-007/009 on a NULL-expiry batch, and the spot path must not become the hole through which
NULL-expiry rows enter `warehouse_inventory`. If the driver genuinely cannot read an expiry, that is
a `verify` task, not a silent NULL. ⛔ **Do not default it to 2099-12-31** — that is the sentinel
shape (P0.4) and it would make spot goods immortal in FEFO.

## 3. TRANSACTION ORDER (one statement, all-or-nothing)

1. Validate: role · supplier is Active walk-in · warehouse exists · lines non-empty · every
   `qty > 0` · every `expiry_date` NOT NULL and `>= CURRENT_DATE` · **pre-auth cap** (§4).
2. Resolve `p_po_id`: if NULL, find today's open walk-in PO for this supplier
   (`purchase_date = CURRENT_DATE AND supplier_id = p_supplier_id AND received_date IS NULL`);
   if found **attach via `add_purchase_order_lines`**, else mint `PO-<yyyy>-SPOT<8 hex>` via
   `create_purchase_order`. ⭐ Attaching is the BUILD SPEC's "addition to today's open walk-in PO".
3. **L2:** auto-close any `pending` driver_task for that po_id.
4. Receive into `p_warehouse_id` (**L1**, own path): stamp `purchase_orders` rows
   (`received_date`, `received_qty`, `purchase_outcome='received'`, price/total, `expiry_date`) and
   INSERT `warehouse_inventory` with `batch_id = <po_id>-SPOT-B<n>`, `status='Active'`,
   `provenance_reason` GUC `'po_receive'`, `snapshot_date = CURRENT_DATE`.
5. Emit `inventory_events` `kind='spot_buy_receive'` per line. ✅ **VERIFIED LIVE (leg 90):** the
   CHECK constraint admits exactly
   `load|venue_fill|return|write_off|spot_buy_receive|driver_confirm|correction|derived_decrement|expired_sold_incident`,
   so the label is correct as spelled. ⛔ **And it carries a SIGN constraint** — a second CHECK
   forces `qty_delta > 0` for `load|venue_fill|spot_buy_receive` (and `< 0` for the consuming
   kinds), plus a global `qty_delta <> 0`. A spot receive is therefore **always positive**; there is
   no "negative spot buy" to express a return, and attempting one raises. ⚠️ Only `correction` and
   `derived_decrement` have ever been written to this table, so `spot_buy_receive` is an
   **unexercised path** — fixture 18 is its first exercise.
6. **L3:** `bind_dispatch_fefo(p_dispatch_date, ARRAY[<official_name>], v_caller)`.
7. Resolve `blocked_demand`: rows for this machine+product still open, `resolved_at = now()`,
   `resolution = 'spot_buy'`, `resolved_by = caller`, `resolution_note`. ⛔ **Resolve only up to the
   qty actually received** — a 4-unit spot buy does not close a 10-unit block. Partial ⇒ leave open
   and record the delta in `resolution_note`; silently closing it is LAW 5.
8. `procurement_events` `spot_purchase_created` with the full payload incl. receipt photo path.
9. `p_dry_run = true` ⇒ do all of the above inside a subtransaction and **RAISE to roll back**,
   returning the would-be result. ⭐ Per **S-133**, a rolled-back dry run does **not** check DEFERRED
   constraints — say so in the return payload rather than implying full validation.

## 4. PRE-AUTH CAPS — parked, per the goal command's PARKING protocol

BUILD SPEC: _"Pre-auth params: class+price cap table (park default: snacks/drinks ≤ AED 15)."_

⭐ **DESIGN DECISION D-D: build the cap as ENFORCED-BY-DEFAULT with a dial, not as a parked no-op.**
Two new `refill_policy_params` columns (the table is a ONE-ROW WIDE table, ✅ **81 columns as
measured live this leg** — the leg-88 pointer's "78" predates leg 89's three miner dials, 78+3=81):
`spot_buy_price_cap_aed numeric NOT NULL DEFAULT 15` and
`spot_buy_cap_enforcement text NOT NULL DEFAULT 'warn' CHECK (IN ('off','warn','block'))`.
Wave 1 ships `'warn'` (mirrors `preflight_enforcement`, which has sat at `'warn'` since PRD-109 and
is the house pattern for a guard CS has not yet burned in). A price over cap lands in the return
payload's `warnings[]` and in `procurement_events`. **The flip to `'block'` is the one-line
DECISIONS-READY item**, not the existence of the cap.
⛔ Rationale for not parking it entirely: an unenforced cap that nobody can see is indistinguishable
from no cap. `'warn'` makes every breach visible from day one at zero ops risk.

    machine-names fleet-wide bind — it fails loudly if someone "simplifies" the call);
  - ⭐ **`still_unbound_no_wh_stock` is surfaced** in the return jsonb, not swallowed;
  - ⭐ **dry run leaves ZERO residue** across all four protected tables (deltas, not absolute counts

## 6. CODY REVIEW — verdict and conditions

**VERDICT: CONSTITUTIONAL, subject to the five conditions below.** The design touches four protected
entities (`purchase_orders`, `warehouse_inventory`, `refill_dispatching`, `blocked_demand`) and adds
a SECURITY DEFINER function, so it is squarely in Article 3/4/6 territory.

1. **Article 3 — versioned additions only.** ✅ Satisfied _because_ of D-A and D-B: the design adds
   `_v3` and **composes** the incumbents rather than editing them. ⛔ The moment a build leg finds it
   "easier" to add a warehouse argument to `receive_purchase_order`, this verdict is void.
2. **Article 6 — `warehouse_inventory.status` is manager-only.** ✅ The RPC only ever INSERTs rows
   `status='Active'`; it must **never** UPDATE `status` on an existing row. A spot buy that finds an
   Inactive row for the same product creates a **new** batch — it does not resurrect the old one.
3. **Article 4 — provenance.** The `app.via_rpc` / `app.rpc_name` GUCs leak across statements in
   this codebase (PRD-016B). ⛔ **Set them immediately before each protected write and RESTORE them
   at the end** — the exact discipline `run_weekly_miners_v3` uses and fixture 60 seq 53/54 asserts.
   Fixture 18 must assert the same restore.
4. **Article 7 — append-only.** ✅ No DELETE anywhere, including the driver task (D-B).
5. **LAW 12 — never touch live plan tables.** ⛔ Fixture 18 runs on a **2030** plan_date and a
   synthetic machine. ⚠️ **S-124 is directly relevant: fixture residue has previously landed on the
   live protected plan table.** `refill_dispatching` is protected and this fixture writes to it —
   the dry-run/rollback discipline is not optional here, and the residue assertion (§5, 46) is the
   one that proves it.

⏸️ **Cody's recorded condition:** the RPC creates the **first** `blocked_demand` resolutions in the
table's history. Until P4.4 ships, `v_blocked_demand_open` has never had a row leave it, so any
aging/burn-down metric built on it is **unexercised**. Do not report "blocked demand is being worked"
off the first week of spot-buy data — that is the G12 lesson (an unfired gate reporting a headline).
